# Task 2. FURPS+ Table: Online Deposit Opening (MVP)

Requirements for the MVP of online deposit applications through the **website** and the **internet bank (IB)**. They are collected from interviews with the business and the IT teams, plus the IT landscape described in [Task1](../Task1).

**Legend**

- **[ASR]**: architecturally significant requirement. It affects the structure of the solution, the choice of technologies, or integration between systems.
- *[Added]*: an extra requirement that was not in the source description. The reason for it is in the "Comment" column.
- **(Task1)** in a comment: the requirement or its reason comes from the company's IT landscape (current systems and processes), not only from the task text.

| Code | Requirements | Comment |
|------|--------------|---------|
| **F** | **Functionality** | |
| F1 | **[ASR]** The website shows anonymous visitors a list of available deposits with current rates. | Today the website shows only marketing information and has no integrations (Task1). The rates have to come from a single source of truth through an integration, not from manual updates of the site. |
| F2 | **[ASR]** A new client can submit a deposit application on the website by entering a phone number and full name. The application is delivered to the bank's call center system. | This is a new integration: website → call center system. The call center system currently only passes inquiries to the ABS. The partner call center has no integration with the bank and is out of MVP scope. |
| F3 | After studying the website application in the call center system, the call center manager calls the client and can offer special conditions. | The call center system must show the application data and its status. The call center platform has CRM functions that the bank does not use today (Task1). They can hold website applications without a new system (+R9). Special conditions mean a special rate. In the current process (Task1) the deposit back office approves it, and that approval is moving into the ABS (F8). |
| F4 | After the call, the new client comes to a branch for identification, and the deposit is opened there. *[Added]* The branch employee can find the client's website application and its agreed conditions by its ID. | Banks cannot onboard new clients without an in-person document check (see +R2). Without a link to the application, the branch has to ask for the agreed special conditions again by e-mail, as it does today (Task1). The link also lets the bank measure how many website applications become deposits. |
| F5 | **[ASR]** An authenticated client in the IB sees the list of available deposits with current rates **and personalized rates** for that client. | Personalized rates need client data, including risk data owned by the credit department. Today the split between deposit and credit data is enforced only by e-mail (Task1). The calculation has to be automated so that credit data is not exposed to the IB. |
| F6 | In the IB, the client specifies an account and a deposit amount and submits an application to open a deposit. *[Added]* Before submitting, the IB checks the amount against the product limits and the account balance. | Without these checks the back office gets applications that cannot be fulfilled, and the client only finds out after a manual review. |
| F7 | **[ASR]** The client confirms the application in the IB with a one-time SMS code. | SMS is implemented in the core system. Changing it requires the vendor, which should be avoided, and the business function can be built by the bank's own development team. The OTP logic (generate, store, check, limit attempts) is therefore built by the bank's team. The core's SMS sending is used only if it works without changes; otherwise the bank's team connects to the SMS gateway directly. |
| F8 | **[ASR]** Deposit rates are maintained in a system instead of XLS files. Employees of both the deposit back office and the credit back office can work with them. A possible option is to implement this in the ABS, together with the whole current rate approval process for applications. *[Added]* Access is role-based: each back office can only do what its role allows. | XLS files cannot be published to channels and have no audit or access control. Today rates are recalculated in Excel once a day from the Central Bank rate and sent by e-mail (Task1). The system must support this daily update and publish the new rates to the channels automatically. The ABS keeps a single master for rates and approvals, and back-office work adds little load. Website and IB channels must still read rates from a published copy or cache, not from the overloaded ABS database (R3, P1, +R3). Role-based access is needed because the credit back office gets access to deposit data (+R8). |
| F9 | In the MVP, a back office manager processes the application to open a deposit and confirms the deposit conditions in the ABS. *[Added]* The solution allows later automatic approval of standard applications without changes to the channels. | Processing stays manual in the MVP. Once the volume of online applications grows, manual processing becomes the bottleneck, so automation should not need a rework of the website and the IB. |
| F10 | **[ASR]** The client receives SMS notifications (1) after the deposit rate is confirmed and (2) after the deposit is opened. | Notifications are triggered by status changes in the ABS. They should be sent asynchronously through events (Kafka, see +R10), not by polling the ABS from the channels. |
| F11 | *[Added]* The client can see the status of the application in the IB (submitted, rate confirmed, deposit opened, rejected). | Without a status the client calls the call center, which adds load. Status is also needed for support and for monitoring the process end to end. |
| F12 | **[ASR]** Data sent from the website must be protected by traffic encryption. *[Added]* Browser ↔ website: HTTPS only, with TLS 1.3 preferred and TLS 1.2 as the minimum. Only AEAD cipher suites with forward secrecy (ECDHE + AES-GCM / ChaCha20-Poly1305) are allowed. SSL 3.0, TLS 1.0 and TLS 1.1 are disabled. HSTS is on (max-age ≥ 1 year) and plain HTTP redirects to HTTPS. Certificates are issued by a trusted CA, use RSA ≥ 2048 or ECDSA P-256 keys, and are renewed automatically. Website ↔ call center system: TLS 1.2+ with mutual authentication (mTLS). Where Bank of Russia regulations require certified cryptographic protection (CIPF), GOST TLS is used on that channel. | The website sends sensitive personal data (full name, phone number). The website has no integrations today (Task1), so the new link to the call center system crosses network zones and must be encrypted as well. The settings follow current industry practice (Mozilla "intermediate" TLS profile, OWASP ASVS V9). Target score on an external TLS check (e.g. SSL Labs): A or higher. |
| F13 | **[ASR]** Data exchanged with the IB must be protected by an encryption mechanism. *[Added]* External perimeter: the same TLS profile as F12. Internal service-to-service calls and Kafka: TLS 1.2+ with mTLS, and Kafka clients authenticate with SASL/SCRAM or mTLS and have topic-level ACLs. At rest: AES-256 for application data (TDE in MS SQL / Oracle, encrypted Kafka volumes and backups). Keys and secrets are kept in a secrets vault or HSM, never in code or configuration files, and are rotated at least once a year. | The source requirement does not name a mechanism. Internal encryption is added because personal and financial data will move through new components (queues, caches, microservices) that did not exist before. Zero-trust inside the perimeter is now standard for banks. |
| F14 | *[Added]* Website forms are protected against bots and abuse: CAPTCHA (or an invisible bot check) on the application form, a rate limit of 5 applications per hour per IP address and 3 per day per phone number, and a WAF in front of the website and the IB. | Anonymous applications without protection can flood the call center with fake applications. A WAF blocks the OWASP Top 10 attack classes before they reach the applications. |
| F15 | *[Added]* All actions with applications, rates and OTP checks are written to an audit log: who (user or employee ID), what (action, old and new values), when (UTC timestamp, NTP-synchronized), from where (IP, channel) and the correlation ID. The log is append-only, protected against changes, and kept for at least 5 years. Personal data in technical logs is masked (e.g. phone `+7 9** *** **12`). | Rate changes and special conditions affect the bank's finances. An audit trail is a typical banking compliance requirement (Bank of Russia rules, GOST R 57580.1) and replaces the e-mail trail used today. 5 years matches the usual retention period for client operation records. |
| F16 | *[Added]* IB authentication and session: the deposit services accept only IB-authenticated requests with a token (OAuth 2.0 / OpenID Connect, access token lifetime ≤ 15 min). The session ends after 15 minutes of inactivity. The OTP is bound to the operation: the SMS shows the amount and the type of operation, and the code is accepted only for exactly that application (the client signs what they see). | The new deposit services sit outside the IB monolith (S1), so they need their own way to trust the IB session. Binding the OTP to the operation protects against substitution of the amount or account between the screen and the confirmation. |
| **U** | **Usability** | |
| U1 | The interface must be as convenient as possible for the client. *[Added]* Measurable targets: (1) an IB application takes no more than 3 screens, including the OTP; (2) a website application needs only 2 fields (full name, phone) plus a consent checkbox; (3) 90% of users complete the IB application in under 2 minutes; (4) at least 90% of test users finish the task without help in usability testing before release. | The business wording "as convenient as possible" cannot be tested. Measurable targets let the solution be accepted and can be tracked with product analytics after launch. |
| U2 | **[ASR]** All new and changed interfaces follow the company's design system for applications, so users see familiar colors and branded elements. | This applies to the client channels (website, IB) and to any new screens for employees (call center, back office). New front ends, including those of the deposit services (S1), reuse the shared UI component library instead of building their own. |
| U3 | *[Added]* The website and the IB are responsive and work in mobile browsers: screen widths from 360 px, the last 2 versions of Chrome, Safari (iOS and macOS), Firefox, Edge and Yandex Browser. Front-end targets on a mid-range phone over 4G: Largest Contentful Paint ≤ 2.5 s, Interaction to Next Paint ≤ 200 ms, Cumulative Layout Shift ≤ 0.1 (Core Web Vitals, 75th percentile). | The bank has no mobile app (Task1), and mobile is the main channel for younger clients. A responsive web UI covers them in the MVP. Server-side speed (P1) means nothing to the client if the page itself loads slowly. |
| U4 | *[Added]* The client always gets clear feedback: confirmation that the application was accepted (with its number), readable error messages without technical codes, and the reason for a rejection. SMS texts use agreed templates and fit into one SMS segment (70 Cyrillic characters) where possible. | Asynchronous processing (R3) means the final result is not immediate, so the client has to understand what happens next. |
| U5 | *[Added]* The interfaces meet WCAG 2.1 level AA accessibility. | A public financial service should be usable by people with disabilities. This also reduces legal risk. |
| **R** | **Reliability** | |
| R1 | **[ASR]** All services work 24/7 with availability of at least 99.9% (no more than 43.8 minutes of downtime per month, 8.76 hours per year). This also applies to the IB. *[Added]* Availability is measured per calendar month as the share of successful requests (non-5xx, within the P1 p99 limit) plus external synthetic checks every minute. Planned releases and maintenance cause no downtime (rolling or blue-green deployment) and count against the budget if they do. | The IB team says this is not achievable today: one DC, one group of servers. Their claim that a day of downtime causes no problems holds only while the IB has few clients. Online deposit sales will increase IB load and business importance. Suggestion: reach 99.9% in stages, with the new deposit services at 99.9% first. Without a stated way to measure it, 99.9% cannot be checked. |
| R2 | **[ASR]** If a DC fails, IB services stay available and handle the required load. Deployment uses the main and the backup DC. *[Added]* Targets: RTO ≤ 15 min; RPO = 0 for applications already confirmed to the client and ≤ 1 min for other data. Each DC can handle 100% of the peak load (P5) on its own. Failover is automatic or a single documented action, and it is tested at least twice a year. | A backup DC already exists, and the bank can switch to it if the main DC fails. The 99.9% budget (R1) is about 43 minutes per month, so RTO has to be well below it. A manual switch that takes hours does not meet R1. RPO = 0 for confirmed applications means the client is never told "accepted" for an application that is then lost: Kafka with replication across DCs (replication factor 3, `min.insync.replicas=2`, `acks=all`) and synchronous database replication for the application store. |
| R3 | **[ASR]** In the new process, the IB should avoid working directly with the ABS API. *[Added]* Interaction goes asynchronously through Kafka, and a failure or slowdown of the ABS does not stop applications from being accepted. | Two reasons from the source: the 99.9% availability target (R1), and the ABS team's statement that its database is already overloaded. Online applications for a large number of products could put the whole bank at risk. Today the IB is integrated with the ABS directly through the Oracle database (Task1). |
| R4 | **[ASR]** *[Added]* Applications and notifications are delivered reliably and exactly once from the client's point of view: at-least-once delivery (Kafka producer with `acks=all` and idempotence on, transactional outbox in each service) plus idempotent processing (each application has an idempotency key, and repeated messages or double clicks do not create a second application or deposit). Messages that fail after 5 retries with exponential backoff go to a dead letter topic and raise an alert. | With an asynchronous process, losing or duplicating a message means a lost client or a duplicate deposit. |
| R5 | **[ASR]** *[Added]* Graceful degradation: every call to another system has a timeout (≤ 2 s) and a circuit breaker. If the rate source is unavailable, the channels show the latest published rates with their timestamp for up to 24 hours, after which applications are paused. If the ABS is unavailable, applications are accepted and queued; the Kafka topic retention (≥ 7 days) covers the longest expected ABS outage. | This keeps channel availability at 99.9% even though the ABS scales only vertically and can be a bottleneck. A slow dependency without a timeout takes down the service that calls it. |
| R6 | *[Added]* Error rate: no more than 0.1% of requests end with a server error (5xx) over any 1 hour. Backups of the application databases: daily full and hourly incremental, kept 30 days, with a restore test at least once a quarter. Mean time to detect an incident ≤ 5 min; mean time to recover ≤ 30 min. | Availability (R1) alone hides partial failures. Backups that have never been restored cannot be trusted. Detection and recovery times connect monitoring (S4) to the availability target. |
| **P** | **Performance** | |
| P1 | **[ASR]** The response to every operation is as fast as possible and takes milliseconds, not seconds. *[Added]* Server-side response time, measured at the API gateway under the target load (P5): <br>• deposit list and public rates: p95 ≤ 100 ms, p99 ≤ 200 ms <br>• personalized rates in the IB: p95 ≤ 200 ms, p99 ≤ 400 ms <br>• submitting an application (website or IB): p95 ≤ 300 ms, p99 ≤ 500 ms <br>• checking the OTP code: p95 ≤ 300 ms, p99 ≤ 500 ms <br>• application status: p95 ≤ 150 ms, p99 ≤ 300 ms <br>No request to the deposit services takes more than 1 s. | "Milliseconds" needs testable numbers, and p99 catches the slow tail that p95 hides. Submitting only accepts the application; processing is asynchronous (R3). The targets can only be reached if channels do not read from the ABS synchronously, so they need their own data store or cache. |
| P2 | **[ASR]** Fix the current problem: during payments in the IB, some reference data takes more than 1 second to load. *[Added]* Target: p95 ≤ 100 ms, p99 ≤ 200 ms for loading reference data. | The problem is in the existing payments flow, not in deposits, but the business asked to fix it. Reference data changes rarely, so it should be cached close to the IB (in-memory or a distributed cache) and refreshed by events, instead of being read from the overloaded ABS database on every request. The same cache can serve deposit rates (P1). |
| P3 | **[ASR]** Services should scale horizontally and evenly, with requests balanced across servers, applications and DCs. The ABS is an exception: it can scale only vertically (+R3). *[Added]* At least 2 instances of each service per DC; autoscaling adds instances when CPU stays above 70% or p95 goes over the P1 target; adding an instance increases throughput almost linearly. L7 load balancing between instances and global load balancing (GSLB / DNS) between DCs. | This applies to the website, the IB and the new deposit services. Services have to be stateless, with session and state kept outside the application instances. Two instances per DC means one instance can fail or be updated without losing capacity. |
| P4 | **[ASR]** *[Added]* The load on the ABS is limited and controlled: messages from the queue are processed at a configured rate that the ABS team agrees to (starting point: ≤ 5 applications per second), and the consumer slows down automatically when ABS response time grows (back-pressure). The new process must not raise ABS database CPU by more than 5 percentage points at peak. | The ABS can scale only vertically because of its database. Its capacity is a fixed limit for the whole process. A measurable limit lets the ABS team check that the new process is safe for them. |
| P5 | *[Added]* The solution is sized for the load model below (target load), and load tests prove 2× the target load without breaking P1. The business confirms or corrects the load model before the design is finished. | Without load figures, P3 and P4 cannot be sized and tested. The model is an assumption based on 10× the expected first-year demand, so it has headroom for marketing campaigns. |
| P6 | *[Added]* OTP: 6 digits, single use, valid for 5 minutes, at most 3 wrong attempts before a new code is needed, and at most 1 resend per 60 seconds. SMS with the OTP is delivered in p95 ≤ 30 s. SMS notifications (F10) are sent within 1 minute (p95) after the status changes in the ABS. Rate changes reach the channels within 5 minutes after approval. | Slow SMS delivery makes the IB application slow and leads to abandoned applications. OTP limits are a usual banking control against brute force and SMS flooding. Freshness targets make "current rates" (F1, F5) testable. |
| **S** | **Supportability** | |
| S1 | **[ASR]** Consider moving the IB to a microservice architecture, for now only within the deposit opening task. *[Added]* The deposit services are built as separate services next to the existing IB, and the rest of the IB stays as it is (strangler pattern). | The source text gives this as an option ("possibly"), not a decision. Limiting it to deposit opening avoids rewriting the whole IB. Separate services can use Kafka even though the IB platform cannot (+R4, +R10), and they can scale on their own (P3). |
| S2 | **[ASR]** The SMS confirmation business function is built by the bank's own development team. Changes to the core by the vendor are avoided. *[Added]* The same applies to the other new functions: notifications and rate publication. | This reduces dependence on the vendor and speeds up changes. Integration with the core uses only interfaces that need no vendor changes. |
| S3 | Documentation is created for future extension of the system. *[Added]* Contents: architecture diagrams (C4 model), ADRs, OpenAPI 3 specifications for every REST API, AsyncAPI specifications and a schema registry (Avro or JSON Schema) for every Kafka event, and runbooks for operations (failover, restarting consumers, replaying the dead letter topic). | The bank plans to move other products online. Without contracts and recorded decisions, every next product starts from zero. |
| S4 | *[Added]* Observability: structured JSON logs in a central store (kept 90 days online); metrics for every service (request rate, errors, p95/p99 latency, Kafka consumer lag); distributed tracing with OpenTelemetry, where the correlation ID passes through HTTP headers and Kafka message headers; alerts on SLO burn rate and on consumer lag. | 99.9% availability and millisecond response times cannot be ensured or proven without monitoring. Asynchronous chains also need tracing to find where an application is stuck. |
| S5 | *[Added]* CI/CD and automated tests for the new services: unit test coverage ≥ 70% of business logic, contract tests for every API and event, load tests at 2× target load before each major release, static and dynamic security scans (SAST / DAST, dependency scan) with no open critical or high findings, and an external penetration test before go-live. Rollback of a release takes ≤ 15 minutes. | Load tests are needed to confirm P1–P5. Contract tests protect integrations between independently deployed services. Security testing before go-live is a standard requirement for internet-facing banking services (OWASP ASVS level 2). |
| S6 | **[ASR]** *[Added]* Deposit products and their parameters are set up through configuration, without code changes in the channels. | The business wants to sell a large number of products online. Adding a product should not need a release of the website and the IB. |
| S7 | *[Added]* API and event versioning: REST APIs are versioned (`/v1/...`), events have a version in the schema, and only backward-compatible changes are made within a version. An old version is supported for at least 6 months after a new one is released. | The channels, the call center system and the ABS adapter are released separately. Without versioning, one change can break the others. |

## Load model (assumption)

The business has not given load figures yet. The model below is the sizing basis for P1, P3, P4 and P5 until the business confirms it. The daily figures already include 10× headroom over the expected first-year demand. RPS = daily volume × 15% (share of the peak hour) ÷ 3600 × 5 (burst factor inside the hour). The target is the calculated value rounded up with extra margin, and never below a minimum sizing of 5 RPS per flow.

| Flow | Basis (per day) | Calculated peak | Target peak load |
|------|-----------------|-----------------|------------------|
| Website: deposit list and rates | 50,000 visitors × ~10 requests | ~105 RPS | 200 RPS |
| Website: applications | ~2% of visitors apply = 1,000 applications | ~0.2 RPS | 5 RPS |
| IB: deposit list and personalized rates | 20,000 active users × ~20 requests | ~85 RPS | 200 RPS |
| IB: submit application, OTP check, status | ~5% of active users apply = 1,000 applications × 3 requests | ~0.6 RPS | 10 RPS |
| IB: reference data (whole IB, incl. payments, P2) | 20,000 active users × ~50 requests | ~210 RPS | 500 RPS |
| Kafka: all deposit events | ~2,000 applications × ~10 events (status changes, notifications) + rate updates | < 5 messages/s | 100 messages/s |
| ABS consumer | throttled (P4) | — | ≤ 5 applications/s |
| Applications in total | website + IB | ~2,000 per day | — |
